# T3 PR lifecycle

Use host tools available in the current session. Discover tool schemas; do not
assume a tool name or argument shape from another T3 version.

## Publication

After creating, taking over, or pushing to a PR, the next tool call links that
PR with link_pull_request (or link_pull_requests for a stack). Pass full URLs.
If linking fails, report it and retain the PR URL in the checkpoint.

## Waiting and wakes

Use watch_pull_request for the open PR even after checks/reviews pass. Finish any branch
update and push first. After attaching the watch, end the turn. T3 wakes the
thread on relevant events; this is the runtime that a skill file alone lacks.

On a watcher wake, read the PR state first. A confirmed merge or closure ends
maintenance; record it, unwatch, and report it before attempting other actions.
For open PRs, refresh the head, checks, reviews, unresolved threads, and conflicts.
The watch persists across wakes and pushes; reattaching on each
wake is unnecessary. If the task was explicitly resumed after a prior unwatch,
attach again if still open.

Green CI means ready for review/merge, not finished. Keep the watch while the PR
is open, including while waiting on human reviews or an external decision.
Report a newly ready head once and return to waiting. New suggestions, failing
checks, or conflicts restart the relevant repair/verification/review cycle.

Use neither shell polling nor gh --watch, sleeps, scheduled polling tasks, or
a delegated child as the PR watcher. Children return work to the parent; the
parent owns publication, progress, and the watch.

Honor project AI review holds. Intentionally cancelled CI is not proof of a code
failure; use the project's hold/resume logic and surface an external stall.

Before a terminal merged/closed report, an explicit user stop, or an ownership
handoff, call unwatch_pull_request for this task's watch. A readiness report or
a recoverable blocker while maintenance remains active does not end the watch.
Waiting on the active watch is not a terminal handoff. If monitoring cannot
continue, report the limitation and preserve progress. Do not stop another
task's watch.

## Delegation

Use native agents for same-provider tasks when supported by the host. Use
delegate_task for another provider, explicit user-selected settings, an isolated
checkout, or a requested delegate task. Read orchestrator_capabilities before the
first delegate_task in a thread. Follow a running delegate's returned next
instruction; do not poll it. Each fresh delegated review is a new task.

Project instructions may require investigators and named reviewers. Preserve
their freshness and context limits. Never create top-level threads just to
simulate subagents. Cancel tasks that are replaced or no longer needed.

## Portability and handoff

Personal Git syncs skill definitions, not live T3 sessions, credentials, user
approval, or active watches. Authenticate the host tools on each laptop.

One thread/machine owns a task's writes. For an explicit handoff, stop the old
watch, transfer the plan and approval evidence through a user-authorized channel,
and identify the receiving thread. Move the local checkpoint only through that
handoff; it is excluded from the skill repository. A new thread must inspect the
approval evidence rather than infer approval from a JSON field.
